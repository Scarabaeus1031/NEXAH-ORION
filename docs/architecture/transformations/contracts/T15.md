## Transformation

- **Purpose:** provide a comparable orientation coordinate while preserving access to the domain-specific calendar source.
- **Conceptual operator:** Phase-3B candidate normalized cycle `τ=((t-t0) mod P)/P`; mapping into the complete Orientation Layer is `unknown`.
- **Required parameters:** epoch, period, direction, calendar/timezone profile, normalization profile, target Orientation field definitions, lossiness profile.
- **Optional parameters:** labels, display granularity, visualization-only markers.
- **Expected output:** normalized coordinate and domain tag with complete transition-chain provenance and no added semantic meaning.
- **Known limitations:** the minimum Orientation Layer schema and domain-field mapping are not documented; normalization can flatten domain detail.

## Preserved Invariants

- **Identity:** source calendar representation identity.
- **Provenance:** entire transition chain, calendar/normalization profiles, lossiness, and contract version.
- **Orientation Object ID:** unchanged.
- **Source references:** calendar representation and upstream source references retained.
- **Epoch:** required and preserved.
- **Known constants:** explicit period, epoch, and normalization constants only; no values registered by Phase 3C.

## Lossiness

- **Information preserved:** cyclic order, normalized phase, direction, epoch, period/profile, domain tag, and trace-back.
- **Information hidden:** calendar labels, local conventions, and upstream geometry when retained by reference.
- **Information aggregated:** multiple dates separated by complete periods into one normalized coordinate.
- **Information discarded:** absolute cycle count or calendar detail when omitted by the declared profile.
- **Unknown:** semantic/domain loss until the Orientation Layer fields and lossiness profile are defined.

## Evidence

- **Current evidence level:** `E1`; normalization is architecturally plausible, but the target contract is incomplete.
- **Missing evidence:** authoritative Orientation Layer fields, domain-tag rules, normalization/lossiness profile, cycle-count policy, renderer compatibility profile.
- **Required datasets:** versioned calendar fixtures with epoch/period/direction, expected normalized coordinates, cycle boundaries, repeated-cycle cases, source chains, and domain metadata.
- **Open questions:** Which fields constitute the minimal Orientation Layer? How does domain meaning remain reachable without becoming part of normalization?

## Validation

- **Input validation:** valid calendar/profile/version, epoch, period, direction, units, timezone/boundary conventions, provenance.
- **Output validation:** normalized-range/profile conformance, domain tag, epoch/period/direction, source chain, lossiness declaration, representation version.
- **Invariant checks:** Orientation Object ID, cyclic order, normalized phase, direction, epoch, source references, full provenance.
- **Failure conditions:** undefined target fields, missing epoch/period/profile, hidden normalization defaults, discarded source chain, semantic inference, or execution before candidate approval.
