## Transformation

- **Purpose:** expose a documented polyhedral address or landmark as a calendar segment or position.
- **Conceptual operator:** `unknown`; Phase 3B contains only a lookup placeholder, not an established mapping.
- **Required parameters:** documented face/cell/landmark-to-calendar mapping, polyhedron profile, ordering, epoch, cycle/segment duration, calendar/timezone/boundary rules, within-face treatment.
- **Optional parameters:** labels, display granularity, visual grouping.
- **Expected output:** calendar coordinate with full source address, mapping, epoch, ambiguity, and aggregation provenance.
- **Known limitations:** it is unknown whether faces, vertices, edges, landmarks, or local coordinates drive the calendar.

## Preserved Invariants

- **Identity:** source cell/landmark identity by reference.
- **Provenance:** polyhedron profile, mapping profile, calendar profile, aggregation, and contract version.
- **Orientation Object ID:** unchanged.
- **Source references:** face/cell/landmark, local-coordinate status, and source stellar point retained.
- **Epoch:** preserved when present; never inferred.
- **Known constants:** none registered; future ordering, segment, and mapping constants must be explicit.

## Lossiness

- **Information preserved:** source address/landmark, declared order, epoch, and trace-back.
- **Information hidden:** polyhedral geometry, adjacency, sky metric, and within-face position.
- **Information aggregated:** faces/cells/landmarks sharing one calendar segment.
- **Information discarded:** intra-cell position and unused topology when absent from target metadata.
- **Unknown:** exact lossiness and invertibility because the operator is unknown.

## Evidence

- **Current evidence level:** `E0`; no cell/landmark-to-time assignment is available.
- **Missing evidence:** authoritative address type, ordering, lookup/operator, epoch, calendar profile, segment boundaries, aggregation and ambiguity policy.
- **Required datasets:** versioned address-to-calendar fixtures covering faces/cells/vertices/edges as applicable, boundaries, ambiguous/unmapped inputs, epoch, and source landmark references.
- **Open questions:** Which polyhedral feature is authoritative? How is it mapped to calendar units?

## Validation

- **Input validation:** valid map/profile/version, canonical source address, local-coordinate and epoch status, source references, provenance.
- **Output validation:** mapping/calendar versions, segment/date, epoch/cycle, ambiguity/aggregation status, complete source trace-back.
- **Invariant checks:** Orientation Object ID, source address/landmark references, declared order, epoch, provenance.
- **Failure conditions:** absent mapping/operator, unknown address semantics, implicit ordering/calendar defaults, unresolved ambiguity, provenance collapse, or any execution while operator status is `unknown`.
