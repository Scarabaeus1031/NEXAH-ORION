## Transformation

- **Purpose:** expose a declared stellar phase as temporal recurrence and calendar position.
- **Conceptual operator:** Phase-3B candidate phase-to-time relation `t=t0+(P/(2π))θ mod P`; the controlling stellar coordinate is undocumented.
- **Required parameters:** selected angle/phase rule, epoch, period, direction, angular/time units, calendar system, timezone, date-boundary convention.
- **Optional parameters:** display granularity, documented intercalation profile, labels.
- **Expected output:** calendar position retaining source phase, epoch, cycle, conventions, and trace-back.
- **Known limitations:** selected angle, cycle combination, calendar system, epoch, and conventions are missing; phase alone does not establish absolute chronology.

## Preserved Invariants

- **Identity:** selected stellar point/phase identity.
- **Provenance:** source frame/epoch, phase rule, calendar profile, cycle, and contract version.
- **Orientation Object ID:** unchanged.
- **Source references:** stellar point/phase and source representation IDs retained.
- **Epoch:** required and preserved.
- **Known constants:** period and conversion constants only when supplied by a versioned profile; none registered.

## Lossiness

- **Information preserved:** cyclic order, phase, direction, epoch, cycle/profile, and source trace-back.
- **Information hidden:** full sky position and spatial neighborhood.
- **Information aggregated:** directions or cycles sharing a calendar segment under the future rule.
- **Information discarded:** unused spherical coordinates and absolute cycle count when omitted.
- **Unknown:** calendar discontinuities and combined-cycle behavior until profiles are documented.

## Evidence

- **Current evidence level:** `E0–E1`; phase-to-time is a candidate, but all authoritative parameters are absent.
- **Missing evidence:** controlling angle, epoch, period, direction, calendar/timezone rules, cycle-count policy, landmark mapping.
- **Required datasets:** versioned stellar phase/time fixtures with frames, epochs, angular units, expected calendar coordinates, cycle boundaries, timezone/date-boundary cases.
- **Open questions:** Which stellar coordinate drives the calendar? How are multiple cycles combined?

## Validation

- **Input validation:** valid source/frame/version, selected phase coordinate and unit, epoch, source provenance.
- **Output validation:** calendar/profile versions, time units, epoch, period, direction, cycle status, source trace-back.
- **Invariant checks:** Orientation Object ID, cyclic order, phase, direction, epoch, source references, provenance.
- **Failure conditions:** missing phase rule/epoch/profile, incompatible units, implicit timezone/boundary, lost cycle status, inferred chronology, or execution before candidate approval.
